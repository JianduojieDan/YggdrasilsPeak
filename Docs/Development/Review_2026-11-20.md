# Code review of the 2026-11-19/20 night changes (verified)

Three areas were reviewed, and a second agent tried to disprove every finding. Only the findings that survived are listed. Nothing is applied yet; fix after the A4 work, with a build.

## Survival and bots: 7 real of 9 checked

- **If you die during the summit beat, the summit screen never shows, and the save already says the summit was reached** (`Source/YggdrasilsPeak/Survival/ExpeditionComponent.cpp:343`)
  - Why it is real: Confirmed in code. UpdateCamps (434-438) sets bSummitReached and calls SaveCheckpoint->WriteSave before the beat. TickSummitBeat skips FinishSummitBeat when bDead. Respawn->TeleportNear resets CurrentCamp, so the next UpdateCamps sees the summit again, but bSummitReached is already true. It takes the normal camp branch ('Summit - shelter'). Nothing else calls ShowSummit. Quitting or a crash during the beat ends the same way after LoadSavedExpedition. How likely: being sheltered adds only +4 SpO2 (1.5/s), and hypoxia damage is 0.6/s. So death in the ~8 s window needs about 5 health or less on arrival. That is narrow but reachable for a real player. The noo2 bot actually died at 8552 m and never reached the summit, so the example is hypothetical. Real, but low-medium.
  - Fix: Add bool bSummitScreenPending (also saved in UYggSaveGame). In UpdateCamps' summit branch set bSummitScreenPending = true before SaveCheckpoint. In FinishSummitBeat set bSummitScreenPending = false; WriteSave(). At the end of Respawn() and LoadSavedExpedition(): if (bSummitScreenPending) { if (!StartSummitBeat()) FinishSummitBeat(); }.

- **Bot uses the saved summit flag as 'reached this run' and writes over the real save outside -YggNoSave (PIE, -UseSave)** (`Source/YggdrasilsPeak/Survival/YggSummitBot.cpp:345`)
  - Why it is real: HasReachedSummit() returns bSummitReached, and LoadSavedExpedition restores it from the save unless -YggNoSave is set. The command help itself says 'run it in the game or PIE', and PIE has no -YggNoSave. So the first Up tick reports SUMMIT at 0:00, and the Down phase ends at once (S <= 200). Begin->TeleportToCamp->TeleportNear resets CurrentCamp, and the next UpdateCamps saves a South Col checkpoint (bottles already zeroed in noo2, line 280) over the player's save. run_bot.ps1 passes -YggNoSave by default and keeps a backup copy, so only PIE, a manual console run or -UseSave are hit. YggRouteCheck already refuses to run without -YggNoSave for exactly this reason (2026-11-14). The summit bot lacks that guard.
  - Fix: At the top of Run(): if (!FParse::Param(FCommandLine::Get(), TEXT("YggNoSave"))) { UE_LOG(LogYggSummitBot, Warning, TEXT("SummitBot: needs -YggNoSave (it would overwrite your save). Use Tools/Bot/run_bot.ps1 -Chapter summit.")); return; }. Optionally also store bSummitAtStart = Ex->HasReachedSummit() in Begin and require !bSummitAtStart in the Up check.

- **Run() does not reset NextSample, NextCheck or bShotPending, so a second run in the same session records almost nothing** (`Source/YggdrasilsPeak/Survival/YggSummitBot.cpp:132`)

After Stop, or with ygg.Bot.Summit.Quit 0, Phase goes back to Idle and the same world subsystem can run again. Check() then returns early and Sample() is skipped until GameT passes the old run's time. The bShotPending carry-over only happens when a shot never returned (see the screenshot finding), but resetting it is still correct.
  - Fix: In Run(), next to the other resets: NextSample = NextCheck = 0.0; bShotPending = false; PendingShot.Reset(); if (ShotHandle.IsValid()) { UGameViewportClient::OnScreenshotCaptured().Remove(ShotHandle); ShotHandle.Reset(); }

- **A screenshot that never comes back blocks all later pictures (no timeout, unlike YggCameraRecorder)** (`Source/YggdrasilsPeak/Survival/YggSummitBot.cpp:771`)
  - Why it is real: bShotPending is cleared only in OnShot. The minimize trigger itself is not proven, but the 'consumed without callback' path is real. CamRec added its own timeout for 'a request that never came back'. Low severity.

In Tick: if (bShotPending && FPlatformTime::Seconds() - ShotAt > 5.0) { UGameViewportClient::OnScreenshotCaptured().Remove(ShotHandle); ShotHandle.Reset(); bShotPending = false; Note(FString::Printf(TEXT("picture %s lost (no capture in 5 s)"), *PendingShot)); PendingShot.Reset(); }. In Deinitialize: if (bShotPending && FScreenshotRequest::IsScreenshotRequested()) { FScreenshotRequest::Reset(); }.

## Camera and body: 7 real of 9 checked

- **bSliding stays true after every landing, so normal walking pins the swinging boot to the ground** (`Source/YggdrasilsPeak/Survival/FirstPersonBodyComponent.cpp:798`)
  - Why it is real: Confirmed. bSliding and SlideHold are written only inside DetectSlide (grep shows no other writer). Because of the || short-circuit, DetectSlide does not run while IsMovingOnGround() is true. The early returns for climbing and posed poses also skip it. On the last falling frame before a landing, the capsule is less than 14 cm above the floor (a jump lands at about 7 cm per frame at 60 fps). The sweep accepts flat ground (normal Z >= cos 80), so that frame sets bSliding = true, and it then stays frozen for as long as the climber walks. ygg.Feet.Slide defaults to 1. With bSliding stuck: line 822 sets AnimHeight = 0, so PlaceFeet computes Planted = 1 and WantSole = the ground for the swinging leg. The lower clamp (-25 - SlideTuck) lets the boot reach the ground, and UpdateFootDrop counts both boots as resting. Every effect the finding describes follows.
  - Fix: In UpdateFootDrop, run the test every frame: `const bool bSlide = DetectSlide(DeltaTime); const bool bOnGround = Movement->IsMovingOnGround() || Movement->MovementMode == MOVE_None || bSlide;`. In DetectSlide, clear the state when not falling: `if (!Movement || !Movement->IsFalling()) { SlideHold = 0.f; bSliding = false; return false; }` (before the sweep). Optionally also set bSliding = false and SlideHold = 0 in the IsClimbing and bPosedVisual early returns.

- **The slide test accepts flat ground and upward motion, so every jump take-off counts as sliding** (`Source/YggdrasilsPeak/Survival/FirstPersonBodyComponent.cpp:929`)
  - Why it is real: Confirmed. The only filters are !bStartPenetrating and ImpactNormal.Z >= cos(80 deg), with no walkability check and no vertical-speed check. On the take-off frame CharacterMovement is already Falling and the capsule is only a few cm up, so the hit counts as contact and bSliding is held for about 0.25 s plus the contact frames. During that time bOnGround is true and AnimHeight = 0, so each leg's Need becomes 'how far the capsule has risen' and FootDropTarget climbs toward MaxPelvisDropCm (70). The ground trace reaches FloorZ - 150, so the ground is still found while rising. The rig reads GetFootDrop (YggViewRig.cpp:1758-1762), capped at FootDropMaxCm = 10, so the eye dips mid-jump. Players can jump (SurvivalComponent::DetectJump charges stamina for it), and YggRouteBot.cpp:541/562 and YggSummitBot.cpp:495 call Jump().
  - Fix: In DetectSlide, only enter the sweep when `Movement->Velocity.Z <= 50.f`, and accept a hit only on ground you cannot stand on: `&& !S.bStartPenetrating && !Movement->IsWalkable(S) && S.ImpactNormal.Z >= FMath::Cos(FMath::DegreesToRadians(80.f))` (IsWalkable(const FHitResult&) is public and const). This also stops a landing on flat ground from counting as a slide. The every-frame call from finding 1 is still needed for a slide that ends on walkable ground.

- **The 16 cm eye-forward offset switches on and off in one frame at every takeover edge** (`Source/YggdrasilsPeak/Survival/YggViewRig.cpp:1798`)
  - Why it is real: Confirmed. ygg.View.EyeFwd defaults to 16, and InTakeover() (YggViewRig.h:766) is Fall || Knock || TakeFade > 0. ComposeEye writes E straight to Camera->SetWorldLocation, with no smoothing after it. EyeHorizMaxCm = 24, so on level ground the clamp does not hide the 16 cm. At Knock start, TakeLoc is about 0 on the first tick, so the eye moves back 16 cm in one frame with the eyes open. At Knock end, Scripted becomes None and the eye moves forward 16 cm. The same happens when a watchdog or fallback TakeFade starts and ends, and at Fall start. Chapter1.ygs:1405 uses a knock, so this is reachable. The fall end with lids shut is hidden by the Cut. The Sit/Lie/Crawl part is only a comment mismatch: H changes smoothly in those postures, so they cause no jump.
  - Fix: Add a member `float EyeFwdW = 1.f;` and in ComposeEye: `EyeFwdW = ExpTo(EyeFwdW, InTakeover() ? 0.f : 1.f, 0.07f, Dt); E += Fwd * CVarViewEyeFwd.GetValueOnGameThread() * FMath::Clamp(H / StandEyeCm, 0.5f, 1.2f) * EyeFwdW;`. Set EyeFwdW = 1 in HardReset, and to its target where the fall snap calls Cut(), so the jump stays behind the closed lids. Fix the comment to say 'all postures'.

- **The 'hold the fallen view until the lids shut' wait does not hold: the eye jumps about 50 cm up and 16 cm forward** (`Source/YggdrasilsPeak/Survival/YggViewRig.cpp:2296`)
  - Why it is real: Confirmed, and it is worse than reported. In the wait state (Scripted None, TakeFade 0, bFallSnapPending true), InTakeover() is false. ComposeEye then applies the walking band clamp (Lo = 156-6-15-6-4-3 = 122 cm vs. a fallen eye near 71 cm) and adds EyeFwd back. The view clamp at line 2069 also drops RollMax from 30 to RollMaxDeg = 2, so the 30 deg roll snaps to 2 deg. When the 0.6 s fallback sets TakeFade > 0, the roll goes back to 30 and the eye drops again before easing. The Watchdog guards bFallSnapPending (line 3032), but InTakeover and the roll clamp do not. The wait only lasts beyond the fall-end frame when the lids are not shut: normally they shut about 0.05*S before the end and the snap runs in the same tick. So it needs a hitch near T = 1.3 or a beat that opens the lids. Rare, but that is exactly the case the code was written for.
  - Fix: YggViewRig.h:766: `bool InTakeover() const { return Scripted == EYggScripted::Fall || Scripted == EYggScripted::Knock || TakeFade > 0.f || bFallSnapPending; }`. At YggViewRig.cpp:2061, use the fall limits during the wait too: `if (Scripted == EYggScripted::Fall || bFallSnapPending) { MinP = -72.f; MaxP = 80.f; RollMax = RollMaxFallDeg; }`.

- **A fall longer than 2.5 s loses its lease early and goes back to the old 0.3 s spin** (`Source/YggdrasilsPeak/Survival/YggViewRig.cpp:2222`)
  - Why it is real: Real but latent. YggStory.cpp:2648 clamps only the minimum (Max(0.3, ...)), and Fall() accepts any S > 0.2. The lease is Min(S+0.5, 3), and AcquireLease clamps it again to LeaseCap(Fall) = 3 s (YggViewRig.cpp:596). Leases tick on the same real-time clock as ScriptT. So with S > 2.5, the Watchdog (line 3023) ends the takeover with a 0.3 s ease and resets dilation before the lids slam at 0.867*S. The behaviour is as described. No current content triggers it: Chapter1.ygs:552 and YggStory.cpp:3907 both use 1.5.   - Fix: Clamp the length in one place, in UYggViewRigComponent::Fall: `const float S = FMath::Clamp(Seconds > 0.2f ? Seconds : 1.5f, 0.2f, 2.5f);` (log a warning when clamped). In YggStory.cpp:2648, use `FMath::Clamp(JNum(A, TEXT("fall"), 1.5f), 0.3f, 2.5f)` so the beat's wait matches. Alternatively raise LeaseCap(Fall) and use S + 0.5.

- **Probe grid cells start their trace and capture at the capsule's height, which is inside the ground uphill on steep slopes** (`Source/YggdrasilsPeak/Survival/YggGroundProbe.cpp:227`)
  - Why it is real: Real but small, and only in the debug tool. Every cell uses Top = Cap.Z + 300 and From = Cap.Z + 400, not the cell's own ground (the comment at line 56 says '4 m above the collision there', which is wrong). With Cap.Z about 0.9 m over the axis ground, Top is under an uphill corner cell's surface once the slope is steeper than about 54 deg (2.83 m * tan > 3.9 m). The capture start goes under it past about 60 deg. Edge cells need more than 60-63 deg. A downward trace that starts under the surface can only find a lower surface, or nothing. So at the steepest A6 spots (up to 61 deg), 1-3 of the 25 cells report wrong values, and the grid mean, min and max are biased. The axis, boot and eye probes are near the axis and are not affected.   - Fix: In the Under lambda, raise the start with the distance, then capture from the cell's own collision: `const double Reach = FVector::Dist2D(P, Cap) * 2.0; Col = CollisionZ(W, C, P, Top + Reach, Hh) ? Hh.ImpactPoint.Z : NaN; Vis = VisibleZ(C, P, FMath::IsNaN(Col) ? From + Reach : Col + 400.0);`. That covers slopes up to about 63 deg and matches the comment.

- **ygg.GroundProbe.Go teleports without the rig's HardReset or Cut** (`Source/YggdrasilsPeak/Survival/YggGroundProbe.cpp:106`)
  - Why it is real: Real, low (debug command only).   - Fix: After TeleportTo (include Survival/YggViewRig.h): `if (bOk) { if (PC->PlayerCameraManager) { PC->PlayerCameraManager->SetGameCameraCutThisFrame(); } if (UYggViewRigComponent* R = UYggViewRigComponent::Find(C)) { R->HardReset(FRotator(Pitch, Yaw, 0.f), EYggView::Walk); } else { PC->SetControlRotation(FRotator(Pitch, Yaw, 0.f)); } }` (HardReset sets the control rotation itself).
